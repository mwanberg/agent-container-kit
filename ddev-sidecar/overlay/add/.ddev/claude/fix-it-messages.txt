# Fix-it messages: the text of every block the kit prints when it stops an
# image build, a sidecar start or a launch, and of every deny or ask the guard
# hooks give in a session. This file is the only copy of that text; fix-it.sh,
# beside it, prints one block by id.
#
# The image build bakes both files into /usr/local/lib/agent-container-kit/,
# where the build checks, the firewall and the guard hooks read them. Without
# the baked copy the hooks fall back to fixed texts that give only the id. The
# launcher, `ddev claude`, runs the project's copy on the host.
#
# tools/message-ids.py, run from the kit's root folder as
# python3 -I tools/message-ids.py ddev-sidecar, lists every id a kit file names
# that this file lacks and every id this file defines twice, both of which
# fail the run, and every id no kit file names.
#
# Format, one line per part, read line by line with no other tools:
#
#   [id]              starts a message; the id is printed in its header
#   stage: BUILD      or STARTUP, LAUNCH or GUARD; the header reads AGENT-CONTAINER-KIT: <stage> STOPPED
#   failed: ...       what failed
#   asks: ...         in place of stage: and failed:, in a block that prompts
#                     the user to approve instead of stopping; the header reads
#                     AGENT-CONTAINER-KIT: GUARD ASKS and the text follows unlabelled
#   means: ...        what that means
#   fix: ...          one numbered step per line, at most three, the last the
#                     one that applies the fix
#
# {name} in any part is a value the caller passes as name=value. A block is at
# most six lines, with the line that matters most last, so that as much of it
# as possible survives in Docker's failure summary, which repeats the end of a
# failed step's output.

# ---- Sidecar start: the firewall --------------------------------------------

[firewall-not-root]
stage: STARTUP
failed: The sidecar firewall was run without root, so it changed nothing.
means: The firewall runs as root only through the sidecar's one sudo permission, which `ddev start` and `ddev claude` use.
fix: Run `ddev claude`, which re-runs the firewall through sudo before opening a session.

[firewall-tool-missing]
stage: STARTUP
failed: The firewall needs `{tool}`, which the sidecar image does not have.
means: Without it the firewall cannot build or verify its rules, so the sidecar does not start and `ddev claude` opens no session.
fix: Find the step in `.ddev/claude.local/Dockerfile.fragment` that removes packages (`apt-get purge`, `apt-get remove` or `--auto-remove`) and keep the package that provides `{tool}`.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-cannot-close]
stage: STARTUP
failed: The firewall could not set its DROP policies: `{command}` exited with status {status}.
means: The firewall cannot filter traffic in this container, so the sidecar does not start.
fix: Check that `ddev utility compose-config` lists `NET_ADMIN` and `NET_RAW` under `cap_add` for the claude service, as `.ddev/docker-compose.claude.yaml` grants them.
fix: Run `ddev restart`.

[firewall-ipv6-failed]
stage: STARTUP
failed: The container has IPv6 addresses, and the firewall could not {step}.
means: Unfiltered IPv6 would bypass every IPv4 rule, so the sidecar does not start and `ddev claude` opens no session.
fix: Run `ddev restart`.
fix: If it stops here again, the Docker host cannot filter IPv6 for containers: turn on IPv6 filtering in the host's kernel or turn IPv6 off on the project's Docker networks, then run `ddev restart`.

[firewall-step-failed]
stage: STARTUP
failed: The firewall stopped at line {line_no} of /usr/local/bin/init-firewall.sh: `{command}` exited with status {status}.
means: Every default policy stays DROP, so nothing gets out beyond the rules already installed, and the sidecar does not start or `ddev claude` opens no session.
fix: Read the lines above this block for the failing command's own error.
fix: Run `ddev restart`; if it stops at the same line again, compare `.ddev/claude/init-firewall.sh` with the kit's copy and undo any change.

[firewall-lock-busy]
stage: STARTUP
failed: Another firewall run held the firewall's lock for over 60 seconds.
means: A container start and a `ddev claude` launch, or two launches, overlapped; this run changed nothing and opened no session.
fix: Wait a minute, then run `ddev claude` again.
fix: If it stops here again, run `ddev restart`, which ends any stuck run.

[firewall-config-untrusted]
stage: STARTUP
failed: The firewall rejected {file}: it {problem}.
means: The firewall reads its settings only from root-owned, read-only files the image build writes, so the sidecar does not start.
fix: Restore the lines that write /etc/agent-container-kit/ in `.ddev/claude/Dockerfile.base` from the kit's copy, and remove any step in `.ddev/claude.local/Dockerfile.fragment` that writes there.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-domains-crlf]
stage: STARTUP
failed: The egress domains list has Windows (CRLF) line endings, first at line {line_no}.
means: The firewall reads one domain name per line and rejects the whole list, so the sidecar does not start.
fix: Remove the carriage returns: `perl -pi -e 's/\r$//' .ddev/claude/egress-domains.list`
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-domain-invalid]
stage: STARTUP
failed: Line {line_no} of the egress domains list is not a single domain name: `{line}`
means: Each entry goes to the resolver and into the DNS helper's configuration, so the firewall rejects the list, and the sidecar does not start.
fix: Make line {line_no} of `.ddev/claude/egress-domains.list` one domain name, optionally followed by a `#` comment.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-domains-empty]
stage: STARTUP
failed: The egress domains list names no domain.
means: With nothing allowlisted Claude Code cannot reach Anthropic, so the firewall stops and the sidecar does not start.
fix: Put the kit's domain lines back in `.ddev/claude/egress-domains.list`, starting with `api.anthropic.com`.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-no-gateway]
stage: STARTUP
failed: The firewall found no default route, so it cannot determine which address is the host.
means: It needs the host's address to keep the host unreachable, so the sidecar does not start.
fix: Check that `ddev utility compose-config` lists the `claude-isolated` network for the claude service, as `.ddev/docker-compose.zz-claude-overlay.yaml` declares it.
fix: Run `ddev restart`.

[firewall-allowlist-unresolved]
stage: STARTUP
failed: No domain in the egress domains list resolved to an address.
means: DNS or the network is down, or the listed domains are wrong; any allowlist already in service stays, and the sidecar does not start or `ddev claude` opens no session.
fix: Check that the host is online and that `.ddev/claude/egress-domains.list` names real domains.
fix: Run `ddev claude` again, or `ddev restart` if the sidecar is not running.

[firewall-service-invalid]
stage: STARTUP
failed: The reachable services list holds `{entry}`, which is not a DDEV service name.
means: The firewall accepts only named services and rejects the list, so the sidecar does not start.
fix: Set `CLAUDE_SIDECAR_SERVICES` under `build: args:` in `.ddev/docker-compose.zz-claude-overlay.yaml` to service names separated by spaces, such as `db`.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-web-listed]
stage: STARTUP
failed: The reachable services list names `web`.
means: The web container has unfiltered internet access and serves files the agent can write, so a route to it bypasses the egress allowlist; the sidecar does not start.
fix: Remove `web` from `CLAUDE_SIDECAR_SERVICES` in `.ddev/docker-compose.zz-claude-overlay.yaml`.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-dns-helper-failed]
stage: STARTUP
failed: The firewall's DNS helper, dnsmasq, {problem}.
means: Without it the allowlist cannot follow address changes, so the sidecar does not start or `ddev claude` opens no session.
fix: Run `ddev restart`, which starts the sidecar and its DNS helper afresh.

[firewall-verify-failed]
stage: STARTUP
failed: The firewall's check of its own rules failed: {check}.
means: Egress is not contained, so the firewall stops; a sidecar that was already running keeps these rules until it stops.
fix: Run `ddev stop`.
fix: Compare `.ddev/claude/init-firewall.sh` and `.ddev/claude/Dockerfile.base` with the kit's copies and undo any change.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-web-reachable]
stage: STARTUP
failed: The sidecar can reach the web container: {how}.
means: Web has unfiltered internet access and serves files the agent can write, so this route bypasses the egress allowlist; a sidecar that was already running keeps it until it stops.
fix: Run `ddev stop`.
fix: Remove from `CLAUDE_SIDECAR_SERVICES` in `.ddev/docker-compose.zz-claude-overlay.yaml` any service that is web under another name, remove from `.ddev/claude/egress-domains.list` any domain that resolves to web's address, and undo any change to `.ddev/claude/init-firewall.sh`.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[firewall-web-unresolved]
stage: STARTUP
failed: The name `web` did not resolve in the sidecar, so the firewall could not check that the web container is kept out.
means: Web has unfiltered internet access, so a route to it would bypass the egress allowlist, and the firewall cannot rule one out; the sidecar does not start or `ddev claude` opens no session.
fix: Run `ddev describe` and check that the web service is running.
fix: Run `ddev restart`.

# ---- Launch: ddev claude, on the host ---------------------------------------

[launch-sidecar-stopped]
stage: LAUNCH
failed: The sidecar container {container} is not running, and its recent log holds no stop from the kit.
means: The project is stopped, or the sidecar exited for a reason the firewall did not report; `ddev claude` opens no session.
fix: Read the log lines above this block, if any; `docker logs {container}` shows the whole log.
fix: Run `ddev start`, or `ddev restart` if the project is already running.

[launch-image-not-kit]
stage: LAUNCH
failed: The sidecar container {container} has no /etc/agent-container-kit/image-built-at, which the kit's image build writes last.
means: The sidecar runs an image not built from the kit's Dockerfile.base, such as the add-on's own, which carries none of the kit's managed policy or hooks; `ddev claude` opens no session.
fix: Run `ddev claude rebuild`, which regenerates `.ddev/claude/Dockerfile` from `.ddev/claude/Dockerfile.base`.
fix: Run `ddev restart`.

[launch-workspace-empty]
stage: LAUNCH
failed: The project folder /var/www/html in the sidecar holds nothing but the .ddev and .git folders.
means: The project is not mounted into the sidecar, and a session would report that its files do not exist, so `ddev claude` opens no session.
fix: Check that `ddev utility compose-config` mounts the project folder at /var/www/html for the claude service, as `.ddev/docker-compose.claude-mounts.yaml` declares.
fix: Run `ddev claude rebuild`, then `ddev restart`.

[launch-workspace-unreadable]
stage: LAUNCH
failed: The sidecar's user ({ids}) can read no file in the top two levels of the project folder /var/www/html.
means: The image build gives that user the host user's ids, except an id another account in the image already holds, which the build output names. That exception, an image built before the host's ids changed, or project files closed to those ids leave the project unreadable, so `ddev claude` opens no session.
fix: On the host, compare `id -u` with the uid above, and run `ls -ln` in the project folder to see its files' owners and modes.
fix: If the uid differs, run `ddev restart --no-cache` to rebuild the sidecar with the host's current ids; if Claude Code then cannot save its login or settings, run `ddev stop`, `docker volume rm {volume}` (this signs it out) and `ddev start`, once.
fix: If the uid matches, or still differs after that rebuild because another account in the image holds the host's, give the uid above read access to the project's files on the host, then run `ddev claude` again.
